# 80AI 小程序前端 PRD

> 面向微信小程序的 `uni-app` 前端落地规划文档
> 目标：在**不影响现有 Web 接口与 Web 前端**的前提下，复用 `backend` 用户侧能力，上线微信小程序
> 最后更新：2026-09-03

---

# 一、项目目标

## 1.1 项目背景

当前系统已具备完整的 Web 端能力，以及独立的 Flutter 客户端骨架：

- 创意模版浏览
- 文生图 / 图编辑
- 局部重绘
- 提示词反推
- 历史记录
- 积分体系
- 后台管理
- FastAPI 主后端部署在 CloudBase 云托管，公网 HTTPS 已对 Web / 支付宝回调开放

现阶段计划新增一个独立的微信小程序前端，使用 `uni-app` 作为开发框架，复用现有 `backend` 的接口、任务体系和存储方案，降低重复开发成本。

本 PRD 不替代现有 `prd.md`，也不替代 `prd-app.md`。它专门用于指导微信小程序前端的产品范围、技术落地和实施节奏。

## 1.2 项目目标

本项目目标如下：

1. **第一原则：不影响现有 Web。** 不改 Web 已有接口契约，不改 `frontend/` 页面与请求逻辑，不中断 Web 登录、生图、历史、支付、管理后台。
2. 新建独立的 `uni-app` 小程序前端项目，与 `frontend/`、`flutter_app/` 隔离，禁止把小程序改动回写进 Web 工程。
3. 复用现有 `backend`（CloudBase 云托管上的 FastAPI）的大部分用户侧接口，不另起一套小程序后端，也不使用 `backend-api`。
4. 小程序登录采用微信授权登录，并最终换取当前业务系统自己的 JWT。
5. 第一阶段仅上线用户侧核心能力，不做后台管理、画布、SSE 聊天、小程序内支付。
6. 在保证可上线的前提下，优先复用现有 COS、任务轮询、积分扣费和历史记录机制。

## 1.3 成功标准

若满足以下条件，则视为第一期成功上线：

- Web 端原有功能与接口行为与上线前一致（登录、注册、生图、历史、支付、后台）
- 用户可在微信小程序中完成授权登录
- 用户可浏览模版并带入生成
- 用户可上传参考图并提交生成任务
- 用户可查看生成进度与结果
- 用户可查看历史记录
- 用户可看到个人积分和基础账户信息
- 后端无需重构现有任务系统与积分系统
- 小程序能稳定访问 CloudBase 云托管上的 `backend`

## 1.4 不影响 Web 的硬约束

小程序是增量客户端，不是对现有产品的替换或改造。任何实现若可能影响 Web，必须停下来改方案。

**前端隔离**

1. 只新增 `uniapp/`，默认不改 `frontend/` 下任何文件。
2. 不把小程序组件、请求封装、登录态、路由回写进 Web。
3. 不修改 Web 的环境变量、CloudBase 邮箱验证、COS JS SDK 上传、支付宝跳转。
4. 不为小程序去“精简”或重构 `GenerateView.vue` 等 Web 页面。

**接口隔离（只加不改）**

1. 现有 Web 正在使用的路径、方法、请求体、响应字段、状态码、鉴权方式保持不变。
2. 微信登录只新增 `POST /api/auth/wechat/login`，不改 `/api/auth/login`、`/api/auth/register`、`/api/auth/me`。
3. 模板、任务、历史、上传、图片等现有接口不改字段含义，不改必填项，不改默认行为。
4. 小程序需要的差异用新接口或可选字段解决，禁止为迁就小程序收紧或改写 Web 已有参数。
5. 不把现有 `source` 的默认值从 `web` 改掉；若增加 `miniapp`，必须仍接受 `web | app | api`。

**数据与部署隔离**

1. `users` 只允许**新增可空字段**（如 `wechat_openid`），不改现有列的空值约束、唯一约束含义，不要求 Web 用户补微信字段。
2. 微信用户写入随机 `password_hash`、邮箱可空，不得让现有邮箱用户无法登录或无法注册。
3. 同一套库可以共用。只允许**增量加列**的 SQL（如增加可空的微信字段），禁止破坏性迁移、清表、改业务 ID 规则、改积分扣费公式。
4. 云托管保持公网访问；Web、支付宝回调、Flutter 继续走现有 HTTPS 域名。
5. 绑定小程序自定义域名时，使用新域名或新网关规则，不替换 Web 正在使用的后端域名，也不关掉默认公网域名（除非已确认 Web 已切到同等可用地址）。
6. 不关闭、不改写 CloudBase 邮箱验证配置，Web 注册 / 找回密码必须继续可用。

**验收时必须回归 Web**

小程序相关改动合并前，至少手工回归：Web 登录 / 注册、创建生图任务、历史列表、支付宝下单入口、管理后台登录。任一项异常则小程序改动不能上线。

# 二、产品定位与范围

## 2.1 产品定位

微信小程序定位为：

**面向普通用户的轻量化 AI 绘图入口**

它的核心职责不是替代现有 Web，也不是改造现有 Web 接口。Web 仍是主站；小程序只是新增入口，提供：

- 更低门槛的移动端访问入口
- 更顺滑的微信内传播和使用体验
- 更适合用户日常生成、查看结果和复用模版的场景

## 2.2 本期范围

本期纳入范围的功能：

1. 微信授权登录
2. 模版列表与模版详情
3. 文生图 / 图编辑
4. 历史记录
5. 用户中心
6. 积分展示
7. 小程序端图片上传
8. 结果图预览与保存

## 2.3 暂不纳入范围

以下能力不在第一期范围内：

1. 后台管理能力迁移
2. 小程序内用户注册 / 密码登录
3. 小程序内修改密码
4. 小程序内头像上传
5. 提示词反推
6. 局部重绘
7. 多角色后台入口
8. 模版管理、用户管理、接口管理、COS 配置
9. 无限画布
10. SSE 对话
11. 小程序内支付（现有支付宝是 PC 网站支付，小程序不能复用）
12. 对接 `backend-api`（那是对外 API Key 生图服务，不是用户侧账号体系）

说明：

- 第一阶段目标是先跑通最核心的“登录 -> 上传 -> 生成 -> 历史 -> 保存图片”主路径。
- 提示词反推和局部重绘虽然在现有后端已存在，但在小程序端交互复杂度更高，建议在第二期接入。
- 一期积分获取继续走兑换码，或引导用户回 Web 端购买；小程序内买积分需另接微信支付。
- 一期微信登录会新建独立用户，**不会自动登上 Web 邮箱账号**；「Web 注册后绑定微信」放到二期。

# 三、技术策略

## 3.1 前端技术栈

小程序前端采用：

- `uni-app`
- Vue 3
- TypeScript
- Pinia
- 微信小程序原生能力（`wx.login`、`wx.request` / `wx.cloud.callContainer`、相册保存等）

选择原因：

1. 现有 Web 已是 Vue 3 + TypeScript + Pinia，请求封装、登录态、类型可较快对齐后端 JWT 接口。
2. 第一期只做微信，但后续若要出 H5 / App，比从原生小程序再迁一次成本低。
3. 微信特有能力仍直接调原生 API，不被框架挡住。

明确不采用：

| 方案 | 原因 |
|------|------|
| 直接编译 `frontend/` | Web 使用了 Ant Design Vue、DOM、CloudBase JS SDK、`cos-js-sdk-v5`，小程序无法运行 |
| 用 `flutter_app/` 出小程序 | Flutter 面向 iOS / Android，不是微信小程序方案 |
| 微信原生 WXML | 能做，但与现有 Vue 团队栈不一致 |
| Taro（React） | 能做，但会多一套前端栈 |

落地约束：

- 工程新建在 `uniapp/`，**默认零改动 `frontend/`**
- UI 使用 uni-app 组件或微信组件，不要搬 Ant Design Vue
- 上传使用 `cos-wx-sdk-v5` 或走后端 `POST /api/upload`，不要改 Web 正在用的 `cos-js-sdk-v5` 流程
- 登录走 `wx.login` + 后端 `POST /api/auth/wechat/login`，不要改 Web 的 CloudBase 邮箱登录

## 3.2 项目结构策略

当前仓库已具备：

```text
80AI/
├── frontend/                 # 现有 Web 前端
├── backend/                  # 现有 FastAPI 主后端（用户端 / 管理端）
├── backend-api/              # 对外 API Key 服务，小程序不使用
├── flutter_app/              # Flutter 客户端
├── prd/prd.md
├── prd/prd-app.md
└── prd/prd-miniapp-frontend.md
```

后续只新增：

```text
80AI/
└── uniapp/                   # 微信小程序前端项目（独立工程，不改 frontend/）
```

## 3.3 后端复用策略

### 结论

**复用 `backend` 这套云托管服务、同一套用户 / 积分 / 任务库；对 Web 已有接口只读复用、对小程序缺口只做增量新增。不是另起后端，也不是改现有 Web 契约。**

| 层 | 是否复用 |
|----|----------|
| CloudBase 云托管上的 `backend` 进程 | 是，不要再部署一套 |
| MySQL 用户 / 积分 / 任务 | 是，同一套账号体系 |
| JWT、扣费、Celery、COS | 是 |
| 模板 / 任务 / 历史接口契约 | 是 |
| 登录入口 | 否，必须新增微信登录 |
| Web 页面、Ant Design、CloudBase 邮箱验证 | 否 |
| `backend-api` | 否 |

Flutter 已经按同一模式接过：`source` 已支持 `web \| app \| api`，鉴权也是 `Authorization: Bearer <JWT>`。小程序是再加一个客户端。

不建议另起小程序后端：会复制用户、积分、任务、COS、队列，Web / 小程序积分对不齐。

### 拿到 JWT 之后可直接调用的接口

协议是 HTTPS + JSON。小程序 `wx.request` / `callContainer` 可带 Header。`HTTPBearer` 认的就是 `Authorization: Bearer ...`。小程序没有浏览器 CORS 限制。

| 方法 | 路径 | 鉴权 | 用途 |
|------|------|------|------|
| GET | `/api/templates` | 否 | 模版列表 |
| GET | `/api/templates/tags` | 否 | 模版标签 |
| GET | `/api/templates/:id` | 否 | 模版详情 |
| GET | `/api/config/task-scenes` | 否 | 场景、尺寸、积分配置 |
| GET | `/api/auth/me` | 是 | 当前用户与积分 |
| POST | `/api/tasks` | 是 | 创建生成任务 |
| GET | `/api/tasks/:id` | 是 | 查询单任务 |
| GET | `/api/history` | 是 | 历史记录 |
| POST | `/api/images/:id/regenerate` | 是 | 单张重新生成 |
| POST | `/api/upload/credential` | 是 | COS 上传凭证 |
| POST | `/api/upload` | 是 | 后端中转上传（开发兜底） |

任务体沿用现有字段：`prompt`、`model`、`size`、`resolution`、`reference_images`、`num_images`。小程序不用重做扣费、队列、COS 落盘。

当前 Token 有效期为 **1440 分钟（1 天）**。过期后清空本地登录态，重新走微信登录换新 Token。

### 必须新增：微信登录桥接

现有 `/api/auth/login` 要账号 + 密码，`/api/auth/register` 还要邮箱 + CloudBase 验证码。用户表没有微信字段，且 `password_hash` 非空。小程序不能拿微信身份去调现有登录接口。

推荐新增：

- `POST /api/auth/wechat/login`

该接口负责：

1. 接收小程序 `wx.login()` 的 `code`
2. 调用微信 `jscode2session` 换 `openid` / `unionid`
3. 按 `openid` 查找或创建本地业务用户
4. 微信用户可生成用户名（如 `wx_xxxx`），`password_hash` 写随机哈希，邮箱留空
5. 签发当前系统自己的 JWT

这样做的好处：

- 小程序只在登录时使用微信身份
- 登录完成后仍统一走现有 JWT 认证体系
- 后续所有业务接口可与 Web / Flutter 保持一致

不采用以下方案作为一期主方案：

- 直接复用 Web 端账号密码登录
- 直接以 CloudBase Web 邮箱注册体系作为主认证方式
- 让前端仅凭微信侧身份直接访问业务接口
- 依赖腾讯云 CloudBase `callContainer` 自动注入 openid（仅微信云托管有此能力，当前是腾讯云侧 CloudBase，header 不会自动带 openid）

### 上传：接口可复用，客户端实现要换

现有 `POST /api/upload/credential` 发的是 COS STS，给 Web 的 `cos-js-sdk` PUT 直传。小程序没有这套 SDK，`wx.uploadFile` 也是 multipart，对不上。

可行做法：

1. 后端凭证接口不动，小程序使用腾讯云 `cos-wx-sdk-v5`
2. 开发期先走已有 `POST /api/upload` 中转
3. COS 上传域名需加入小程序 `uploadFile` 合法域名

正式上线仍以 COS 直传为主，降低后端带宽与存储压力。

### 任务来源字段

当前 `TaskCreate.source` 仅为 `web | app | api`，历史筛选和后台统计也是这三项。小程序现在只能填 `app`（和 Flutter 混在一起）或默认 `web`（统计会脏）。

一期可不阻塞上线。若要单独看小程序数据，后端把枚举**扩展**为仍接受 `web | app | api`，再增加 `miniapp`；**禁止删除或改名现有枚举值**，以免 Web / 后台筛选报错。

### 不要接到小程序上的模块

- 支付宝 PC 网站支付（`alipay.trade.page.pay`）
- SSE 聊天
- 无限画布
- 管理后台

这些不是“后端不能复用”，是这些模块不要接到小程序一期。

## 3.4 登录策略

本期登录方案采用：

**微信授权登录 + 后端签发业务 Token**

原因：

1. 当前业务系统权限和用户数据均在自有后端数据库中
2. 后端现有接口已经基于 JWT 鉴权
3. 小程序端若直接与微信身份强耦合，会增加后续权限体系维护成本

## 3.5 存储与上传策略

小程序端继续采用现有 COS 直传思路：

1. 小程序向后端请求上传凭证
2. 后端返回腾讯云 COS 临时凭证
3. 小程序用 `cos-wx-sdk-v5` 直传 COS
4. 小程序将最终图片 URL 提交给任务接口

说明：

- 第一版若直传适配成本过高，可先使用后端 `POST /api/upload` 做开发期兜底
- 正式上线建议仍以 COS 直传为主

## 3.6 CloudBase 云托管访问方式

当前 `backend` 已部署在 CloudBase 云托管，公网 HTTPS 可用。支付宝回调示例域名：

`https://backend-80ai-247706-5-1257893314.sh.run.tcloudbase.com`

环境 ID：`banana-ai-4g7iqw0p1cab24e3`（上海）

拦小程序的不是云托管，是微信客户端的域名策略。后端已经对 Web / 支付宝开放；小程序按微信规则发出去即可落到同一套 FastAPI。小程序没有浏览器 CORS 问题。

### 开发调试

微信开发者工具勾选 **「不校验合法域名、TLS、HTTPS 证书」**，可直接请求云托管默认域名，例如：

`GET /api/templates`

模板接口不用登录。能返回 JSON 即证明链路通。真机需开调试模式才跳过校验。

### 正式版两条通路

**方案 A（一期推荐）：`wx.request` / `uni.request` + 备案自定义域名**

1. 给这台云托管绑定已备案自定义域名（例如 `api-web.80ai.net`）
2. **不要误用 `api.80ai.net`**，那是 `backend-api`
3. 小程序后台配置：
   - request：后端自定义域名
   - uploadFile：后端或 COS 上传域名
   - downloadFile：COS 图片域名
4. 小程序 `baseURL` 使用该自定义域名

云托管默认域名 `*.sh.run.tcloudbase.com` 开发期有时能配上，官方不建议当生产入口，微信审核也不稳。

**方案 B：`wx.cloud.callContainer`**

小程序关联同一 CloudBase 环境后，可用云开发私有链路调云托管，不必把后端域名配进 request 合法域名。

约束：

- 必须关联环境 `banana-ai-4g7iqw0p1cab24e3`，不要新开通环境
- `X-WX-SERVICE` 填云托管**服务名**（如 `backend-80ai`），不是完整默认域名
- 腾讯云侧 CloudBase **不会**在 header 自动注入 openid，登录仍走 `code` 换 JWT
- Web、支付宝、Flutter 仍走公网，**不要关闭云托管公网访问**
- COS 出图 / 保存相册仍走 `downloadFile`，仍需配置图片合法域名
- uni-app 中调用 `wx.cloud.callContainer`，不要用 `uni.request` 打默认 `*.tcloudbase.com` 作为正式方案
- 基础库建议 2.23.0+

一期更建议方案 A，请求封装与现有后端、Flutter 完全一致。方案 B 可作为免配 request 域名的备选。无论选哪条，都不得替换或关闭 Web 正在使用的后端访问地址。

## 3.7 小程序关联同一 CloudBase 环境

关联的本质是：把小程序 AppID 绑到现有环境 `banana-ai-4g7iqw0p1cab24e3`，不要再开通新环境。

前置：

1. 微信小程序 AppID
2. 能登录该环境的腾讯云账号
3. 开发者工具 / uni-app `manifest.json` 中的 AppID 与即将关联的一致
4. 小程序与 CloudBase 必须同一主体

### 推荐操作：微信开发者工具

1. 用该 AppID 打开 `mp-weixin` 产物
2. 顶部点「云开发」
3. 若提示开通：**不要点「开通新环境」**，选「使用已有环境 / 关联腾讯云云开发环境」
4. 选择 `banana-ai-4g7iqw0p1cab24e3`
5. 小程序管理员扫码授权

### 备选：CloudBase 控制台

进入环境 `banana-ai-4g7iqw0p1cab24e3`，在「环境设置 / 关联应用 / 登录授权 / 微信公众平台登录」中添加小程序 AppID。

### 备选：微信公众平台

`mp.weixin.qq.com` → 开发 → 云开发。未开过则关联已有腾讯云环境；已绑错环境则改关联或走同主体环境共享。

### 关联后自检

| 检查项 | 正常样子 |
|--------|----------|
| CloudBase 环境设置 | 能看到该小程序 AppID |
| 开发者工具云开发面板 | 当前环境是 `banana-ai-4g7iqw0p1cab24e3` |
| `callContainer` 打 `/api/templates` | 返回模板 JSON |
| 报 env not found / 无权限 | AppID 未绑定，或 `wx.cloud.init` 的 env 写错 |

# 八、后端改造需求

后端改动必须遵守：**只新增、不修改现有 Web 接口行为。** 能不加字段就不改旧接口；能加新路由就不改旧路由。

## 8.1 必需改造

第一期必需改造项如下：

1. **仅新增** `POST /api/auth/wechat/login`，不改现有 `/api/auth/*` 的请求响应
2. `users` 表**只增加可空字段** `wechat_openid`、`wechat_unionid`，不改现有列
3. 微信用户创建时：`username` 自动生成，`password_hash` 写随机值，`email` 可为空；不得影响已有邮箱用户
4. 登录成功后返回现有业务 JWT（与 Web 同一签发逻辑即可，不改 Token 结构）

这是增量改造，不是换后端，也不重构任务 / 积分主链路，不改 Web 前端调用方式。

明确禁止：

- 修改 `/api/auth/login`、`/api/auth/register`、`/api/auth/me`、`/api/tasks`、`/api/history`、`/api/templates`、`/api/upload/credential` 的既有字段与校验

- 修改 `frontend/` 来适配后端的小程序改动
- 收紧 CORS / 关掉公网域名导致浏览器 Web 无法访问（小程序不依赖 CORS，不要借机改 Web 跨域配置）

## 8.2 用户身份映射建议

建议优先采用快速方案：

在 `users` 表增加字段：

- `wechat_openid`
- `wechat_unionid`

说明：

- 现有 `password_hash` 为非空字段，微信用户必须写占位哈希，不能走现有 `register_user`
- 若后续存在多身份体系扩展需求，再考虑拆分独立身份表
- 第一版优先降低实现复杂度

## 8.3 建议同期评估

# 十四、二期方向

在第一期稳定后，可继续规划以下方向。二期仍遵守「不影响 Web 已有接口与 `frontend/`」：只新增接口与小程序页面，不改现有登录 / 注册契约。

## 14.1 账号绑定（优先）

### 目标

让已在 Web 注册的邮箱账号，能和同一用户的微信打通，小程序与 Web 共用积分、历史。

一期默认两套账号并存：

```text
邮箱用户（Web）              微信用户（小程序一期）
email + password             openid + 随机密码哈希
wechat_openid = NULL         email = NULL
```

二期通过绑定把 `openid` 写到邮箱用户上，之后小程序微信登录进入同一条 `users` 记录。

### 为什么不在 Web 页面临时绑定

小程序 `openid` 只能通过小程序 `wx.login()` 获得，浏览器拿不到。Web 个人中心「绑定微信」需要：

- 扫小程序码，在小程序内完成绑定；或
- 微信开放平台网站应用扫码，并依赖 `unionid`

没有开放平台时，**推荐绑定发生在小程序内**，Web 前端可以不改。

### 推荐主路径：小程序内「先登邮箱，再绑微信」

1. 用户已在 Web 用邮箱注册
2. 小程序提供「邮箱登录」（直接调现有 `POST /api/auth/login`，不改该接口）
3. 登录态是这条邮箱用户
4. 用户授权微信，小程序把 `code` 发给**新接口** `POST /api/auth/wechat/bind`
5. 后端用 `code` 换 `openid`，写入**当前 JWT 对应用户**的 `wechat_openid` / `wechat_unionid`
6. 之后 `POST /api/auth/wechat/login` 按 `openid` 找到同一用户，不再新建

### 新增接口（不改旧接口）

| 方法 | 路径 | 用途 |
|------|------|------|
| POST | `/api/auth/wechat/bind` | 已登录用户绑定当前微信 |
| POST | `/api/auth/wechat/unbind` | 已登录用户解绑微信（可选） |

`wechat/bind` 建议校验：

1. 必须已登录（现有 JWT）
2. 当前用户尚未绑定其他 `openid`
3. 该 `openid` 未被其他用户占用
4. 若该微信在一期已自动注册过独立号：提示「该微信已绑定其他账号」，二期前半段先不自动合并积分，避免账务风险
5. 绑定成功后返回最新 `UserBrief`，不改 Token 结构

### 明确不做（二期前半）

1. 不自动合并两个已有账号的积分 / 历史
2. 不改 `/api/auth/login`、`/api/auth/register`、`/api/auth/wechat/login` 的既有字段
3. 不为绑定去改 `frontend/`；若 Web 要展示「已绑定微信」，另立 Web 需求，只读新字段
4. 不把「绑定」做成改现有用户邮箱或强制设密

### 备选后置路径

小程序先微信登录（一期新号），再在设置里绑定邮箱。需要处理「两个已有用户如何合并」，冲突和积分合并更复杂，放到二期后半或三期。

### 二期验收

1. Web 邮箱登录、注册、找回密码行为不变
2. 未绑定用户在小程序微信登录仍走一期逻辑（查找或创建）
3. 已在 Web 注册的用户可在小程序邮箱登录后绑定微信
4. 绑定后，小程序微信登录与 Web 邮箱登录看到同一积分与历史
5. 同一 `openid` 不能绑到第二个用户
